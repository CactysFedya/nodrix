# Принципы Plyctl

Эти принципы являются нормативными для серии 2.x. Возможность не должна
попадать в продукт только потому, что она работает в одной конкретной
интеграции: она обязана сохранять универсальную модель runtime и operations.

## 1. Core остаётся универсальным

Core описывает проект, конечные workflow, runtime-графы, nodes, applications,
resources, контракты, health, metrics и artifacts. В Core не должно быть
специальной логики Livox, FAST-LIVO2, YOLO, камеры или робота. Такая логика
размещается в providers, recipes, project-owned packages, native plugins и
квалифицированных примерах.

## 2. Control plane отделён от data plane

Plyctl управляет lifecycle, readiness, health, зависимостями, логами,
provenance и shutdown. Большие данные идут по подходящему transport:
in-process memory, shared memory, native plugin, ROS 2 DDS, FFmpeg или device
memory. Core не должен десериализовывать изображения и облака точек только
ради наблюдения за pipeline.

## 3. Явные операции без скрытой установки

`plyctl run` запускает уже подготовленный pipeline. Он не должен скрытно
вызывать `sudo`, устанавливать системные пакеты, обновлять репозитории или
пересобирать внешние sources. Setup, source resolution, patching, build и
verify являются отдельными конечными операциями с понятным plan и логами.

## 4. Воспроизводимость важнее удобной магии

Sources фиксируются по commit, patches проверяются, модели и calibration
artifacts имеют идентичность, а каждый run сохраняет resolved configuration и
environment evidence. Автоматизация может запускаться одной командой, но не
должна становиться необъяснимой.

## 5. Проект растёт постепенно

Минимальный проект начинается с `nodrix.yaml`. Каталоги `pipelines/`,
`workflows/`, `packages/`, `calibration/`, `patches/` появляются только тогда,
когда действительно нужны. Templates являются соглашением, а не обязательной
предметной структурой Core.

## 6. Типизированные границы

Ports, external edges, artifacts и provider capabilities используют явные
версионированные контракты. `core.any` допустим для эксперимента, но не для
квалифицированной production-границы.

## 7. Производительность наблюдаема

Latency, queue age, drops, copies, throughput, CPU, RSS, дочерние процессы,
температура и fallback-решения должны измеряться. Заявления о
производительности подтверждаются evidence и regression budgets.

## 8. Безопасное владение процессами

Plyctl завершает только запущенные им процессы. Используются process groups и
сохранённые идентификаторы, сначала выполняется graceful shutdown. Широкие
конструкции `pkill -f` не являются допустимым механизмом управления.

## 9. Offline и edge являются основными режимами

Provider wheels, source locks, patches, checksums, модели и документация
должны собираться в проверяемый offline bundle без обязательного облачного
сервиса и центрального scheduler.

## 10. Совместимость изменяется осознанно

Compatibility-имена 2.x сохраняются согласно политике совместимости.
Изменение schema, ABI, provider, CLI или формата artifacts требует migration
path и отдельного архитектурного решения.

## Проверка новых изменений

При review необходимо ответить:

1. Не добавляет ли изменение предметную логику в Core?
2. Не создаёт ли оно лишнюю копию или Python bottleneck?
3. Можно ли воспроизвести результат на другом устройстве?
4. Можно ли объяснить результат по логам и artifacts?
5. Завершаются ли только процессы, принадлежащие текущему run?
6. Подтверждено ли публичное обещание тестами и evidence?
